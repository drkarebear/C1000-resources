Looking at the actual ENGL C1000 descriptor, I think we can get even more intentional about this collection. The state descriptor is broader than “write an essay.” It explicitly requires students to read/analyze/evaluate diverse texts; apply rhetorical strategies; develop flexible drafting/revision/editing strategies; analyze their own and peers’ rhetorical choices and use feedback; write in multiple genres and modalities; control organization/development/coherence; and identify, evaluate, paraphrase, summarize, quote, and document sources. The outcomes then distill that into analytical reading, thesis-driven writing involving analysis and synthesis of sources appropriate to rhetorical situation, and strategies for planning through proofreading. That tells me something important: we probably don't need many more “chapters.” What we need are small interventions that appear at the exact moment a student is likely to hit a wall. That is where just-in-time instruction becomes especially useful for first-gen students. Instead of expecting students to remember a 30-minute lesson on synthesis from six weeks ago, imagine that right before the first assignment requiring two sources, Canvas says: Need two sources in the same paragraph? Try the 7-minute Synthesis Lab. Or immediately after a student gets a draft back: Got a lot of comments? Try Essay Triage before revising. That changes these resources from a supplementary textbook into a writing support system. For a GitHub Pages activity, the easiest options are browser accessibility checkers. The simplest workflow is WAVE + axe DevTools, then a quick keyboard test. Both can scan the live GitHub Pages URL directly. WAVE Web Accessibility Evaluation Tools — probably the easiest starting point. You can paste in the published GitHub Pages URL, or install its browser extension. It overlays errors, contrast issues, headings, ARIA information, and alerts directly on the page. axe DevTools browser extension — more developer-oriented, but excellent. Open your activity → DevTools → axe DevTools → scan the page. It identifies issues and usually explains how to fix them. Accessibility Insights for Web — useful because it goes beyond an automated scan and walks you through accessibility checks. For our activities, I'd probably use WAVE first because the results are much easier to interpret if you aren't doing accessibility testing professionally. The process could literally be: Publish to GitHub Pages → open the activity → run WAVE → fix red errors → run axe → keyboard-test it. And the keyboard test is surprisingly easy: put your mouse aside and use Tab, Shift+Tab, Enter, Space, and arrow keys. You should be able to start the activity, answer every question, use the end tool, and finish it. You should always be able to tell where keyboard focus currently is. Automated tools can't catch everything. A page can get a perfect automated score while still being miserable with a screen reader. But for catching HTML problems in the activities we're creating—contrast, labels, headings, ARIA, form controls, duplicate IDs, etc.—these tools are excellent. For your project, I think a very manageable standard would be: WAVE: 0 errors → axe: 0 critical/serious issues → complete once keyboard-only → quick VoiceOver check. That gives us a realistic accessibility QA process without turning every new C1000 activity into a giant compliance project. If you're going to test 20+ activities, Accessibility Insights also has value because its structured checks can help you use the same process every time, rather than trying to remember what you checked on each page.
